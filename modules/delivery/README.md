# delivery (changes 007, 008, 039, 041, 042, 044, 045, 081)

Projects, each project's board of specclaw proposals, and releases moving through each project's own environments. "Released" means a release reached the project's Prod environment; a project may have none.

- **Owner:** `/modules/delivery/` in `.github/CODEOWNERS`
- **Screens:** `/delivery` (portfolio), `/delivery/p/:key` (board + environments), `/delivery/proposals[/:phase]`, `/delivery/proposals/:key` (081: one proposal; the segment is a phase when it names one, else a key), `/delivery/releases`, `/delivery/releases/:projectKey/:version`
- **Contracts** (`contracts.ts`): `listProjectRefs`, `getProjectRef`, `managedProjectIds`, `PHASES`, `EVENTS`, `proposalHref`, and the `ReleaseDeployed` / `ProposalPhaseChanged` / `ProposalWithdrawn` / `TaskDone` / `CommitTime` payload types. 081, additive: `getProposalRef(tx, keyOrId)` (Time checks an entry's proposal with it) and `setProposalHours(tx, projectIds, totals)`, through which Time hands over approved hours per proposal for whole projects. Delivery can't read Time (Time depends on Delivery; the graph has no cycles), so this is the only writer of `proposal.hours`. `ProposalPhaseChanged` and `TaskDone` gained an optional `ownerUserId`. 081 amendment 6: `EVENTS.ownerChanged` (`delivery.proposal.owner_changed`, `ProposalOwnerChanged`): from, to and who, raised when a create, `update_proposal` or a Suggested owner accept or undo changes the owner (syncs don't).
- **Project creation (045, for presales' Promote):** `createProject(ctx, { key, name, client, billing, managerName?, sourceRef? })` returns `{ id, key }`, plus `existing: true` when this `sourceRef` already made this key, or `replayed: true` on an idempotency-key replay. A taken key, or a `sourceRef` that made another key, throws `ProjectConflictError` (`existingKey`, not retryable). `sourceRef` is `module.record:id` (e.g. `presales.opportunity:OPP0042`), unique per tenant in `delivery.project.source_ref`, and accepted only through the contract. Callers gate on `PROJECT_CREATE_PERMISSION` (`delivery:project:create`). Additive: earlier callers are unchanged.
- **Events:** `delivery.release.deployed`, `delivery.proposal.phase_changed`, `delivery.proposal.rekeyed`, `delivery.proposal.withdrawn` (081), `delivery.task.done`, `delivery.commit.time`

- **Chat intents** (`chat.ts`): new project, new proposal, new release, record a deployment, change a release. **Chat suggestions** (`chat-suggestions.ts`, 081): New proposal on a project's pages and the list; add a task, edit or withdraw on a hand-made proposal's page
- **Proposals made by hand (081):** an owner (the person acting by default; 081 amendment 6: a named owner must be on the project, holding `delivery:task:done` there, which is a PM who manages it or an engineer assigned to it, else refused before the card; New proposal in chat asks who owns it on a choice card, Me first, then the project's team from Allocations' `get_project_team`, whose rows now carry `userId`), a description, an estimate, tasks added with `add_proposal_task`, and `withdraw_proposal` (a reason; never deleted; leaves its release; gone from lists, counts and boards, readable by key). A spec proposal's content and withdrawal belong to its repo; only its owner can be set in amax. 091 AC-7: a synced or pushed proposal's owner comes from its repo, never from who pushed: the `**Owner:** <email>` header line, else the author of the commit that added its `change.md` (the plugin and CI read it from git), mapped to a person by a verified git identity or their work email, only when they're on the project; otherwise Unassigned. A sync keeps it in step with the repo until a person sets the owner in amax (`update_proposal` or a Suggested owner, audited as `delivery.proposal.update`); from then on it stands. A sync's owner change raises no event but is audited (owner before and after). The email is used for that sync only, never stored (not in `meta`); an author git can't read (a shallow clone, a failure) is unknown, and the stored owner stays. `sync/authors.ts` is the one author lookup, used by the plugin, CI and the self-sync; CI also leaves out a branch whose change folder is already on `main` as it is (a squash or rebase merge).

  card. Board cards carry no action menu: their pin is how you act on them. The proposal page keeps Ask amax and
  Withdraw (an outlined danger button); its pin offers Move, Edit and tasks (amendment 4).

- **Viewer scopes:** contributes each user's managed projects, so `@managed` grants work
- **Ingestion (008):**
  - **Who can call it.** specclaw and CI call `sync_proposal` (with the spec's `committedAt`, 062), `mark_task_done` and `record_deployment`, as a person or as a service credential acting for one. A CI credential should be limited to those three tools (`tools` on `create_api_credential`).
  - **Pushes.** GitHub and Azure DevOps pushes arrive at `/api/webhooks/<tenant>/<provider>`. 035 verifies them (signature, replay window, dedupe) before `inbound.handle`.
  - **Attribution.** A commit counts for a person only when the provider verified it, or when its email is the verified email of their `auth.git_identity`. Such a commit closes the tasks it names (`CON-014 T3 done`). An author who isn't linked but has a person's work email becomes a `delivery.git-identity` suggestion to link them; until an Admin accepts it, that author's commits do nothing.
  - **Commit time.** A `Time: 1.5h` trailer sends `delivery.commit.time` to the time module, which drafts the hours as a suggestion on the person's own timesheet; nothing is logged until they accept. This only happens for a legal entity an Admin switched on with `set_commit_time_logging`, which needs `peopleNotified: true`. Commit data drafts timesheets only: it is never used for ratings, and nothing reads it for performance.
  - **Overview feed.** Each ingested write adds a `delivery.activity` line ("Claude for Nimal", "<credential> for Nimal", "Git for Nimal") to the Overview feed through the manifest's `activity` slot.
  - **Switching off.** With delivery off, the route finds no handler and the Overview shows no feed. With time off, the commit-time event has no reader.
- **Developer pushes (062):** the amax Claude Code plugin (`plugins/amax/`) sends a repo's specclaw state to `sync_specclaw`. amax accepts it only from the project's linked repo (`link_project_repo`, PM or Admin), and only from someone on the project (`delivery:proposal:push`). That permission doesn't open `sync_proposal`, which has none of these checks. A push from the project's default branch (`repo_default_ref`, set with the link, never by a push) covers every change; a push from another branch covers only its own change, and one naming no change is flagged. Per proposal, a push never releases, never moves back a phase, and never applies a commit older than the one the proposal was last pushed from (`proposal.synced_commit_at`). Every specclaw writer moves that mark for each proposal it read, changed or not: pushes, the 039 CLI (`delivery.proposal.mark`), and `sync_proposal`, whose `committedAt` is required. It never creates a project, and withdraws only when asked (089, below). A dry run is the push's transaction rolled back. An applied push is one audited transaction under the project's row lock, which also holds the repo check. A push with nothing new returns `unchanged`: one audit row moves the marks, and the Repo sync card gets no row. A push that changes something, or skips something a person should see (`needsReview`: anything but Released, or on a branch a step back or a stale commit), records a `delivery.sync_push` row. Each applied or refused push is a `delivery.sync_push` row, shown on the project's Repo sync card.
- **CI pushes (089):** `.github/workflows/specclaw-sync.yml` runs `scripts/specclaw-sync-ci.mjs` after a merge to `main` that touches `.specclaw/**`. It calls `sync_specclaw` over REST (`POST /api/v1/tools/sync_specclaw`) with an API credential limited to that tool and acting for the project's PM, so CI gets every check a person's push gets and shows on the Repo sync card as "<credential> for <PM>". It reads the repo with the plugin's own reader, pushes `main` first, then each open `specclaw/*` branch under its own ref (091: a branch already merged into `main`, or whose change `main` has archived, is left out and counted in one summary line; one whose number `main` uses for another folder is left out with a warning), and applies even when `needsReview` is set; skips go to the job summary as warnings. With none of its secrets (`AMAX_URL`, `AMAX_SYNC_API_KEY`, `AMAX_SYNC_ACT_FOR`) it passes with a notice that nothing was synced; with only some, with no changes read on `main`, or on a refused push or HTTP error, it fails. No database URL is needed in GitHub.
- **Withdrawal through a push (089):** with `withdrawMissing: true`, a push from the default branch withdraws a specclaw proposal whose folder is gone (`meta.withdrawn`, never deleted), only when that branch last synced it (`meta.source`), no newer commit has synced it (`synced_commit_at`, the stale rule), and it isn't Released. CI sets it only when one push carries the whole branch (200 changes or fewer); the plugin never does. The rule is one function for the push and the self-sync (`sync/withdraw.ts`, `planWithdrawals`); each withdraws only what a ref it read last synced (the push: the default branch; the self-sync: its records' refs, so a change that exists only on a branch is never withdrawn from main), and a sync that read no changes, or would withdraw more than half of the live proposals (and more than two), withdraws nothing and says so (needsReview). The cap counts only proposals the sync could withdraw (not Released, not synced from another ref). A person confirms a real mass deletion with `confirmWithdraw: <the held count>`; in CI, by running the specclaw sync workflow by hand with `confirm_withdraw`; for the self-sync, with `sync:specclaw --confirm-withdraw <n>`. The count is `withdrawn` in the preview, the result and the push row (`delivery.sync_push.withdrawn`, 0020).
- **History and keys (091):** a push from the default branch brings a finished (archived) change amax has never stored in as Released history, with its archive date, and no phase event or notification; a proposal amax already has is still never moved to Released by a push. A branch push can't take over a key the default branch holds for another folder (skipped as "two changes numbered NNN", needsReview). One commit-sha rule (`sync/sha.ts`) for `sync_specclaw`, `sync:specclaw --sha`/`--overlay` and the ref comparison withdrawal relies on. The Repo sync card groups a push's skips by reason (`ui/skips.ts`).
- **Agent-first projects (093):** a project whose linked repo has brought in at least one proposal (`server/agent-first.ts`, one rule) takes its proposals from the repo only. Its page shows "Proposals come from <repo> · write one with /specclaw:propose" instead of "New proposal"; the global page, chat's suggestions and project choice, and the pin leave it out (`manualProjects`); `create_proposal` and its service refuse it. Hand-made proposals already there stay editable, and unlinking the repo brings manual creation back. The rule counts any proposal a repo sync wrote in the project (withdrawn ones included), so a freshly linked project with none keeps manual creation until its first sync, one that already has some is agent-first as soon as it's linked, and relinking to another repo keeps it agent-first. `list_projects` rows carry `repoUrl` and `agentFirst`.
- **092:** a sync decides whether it may change an owner on the row its upsert locks, so an owner a person sets meanwhile stands. The Owner line's email is matched as a clean address (punctuation and link brackets around it are left out). A Released card says "In Prod" (beside its release chip, 095) only when a Prod deployment released it, and "Released · from repo" for history from the repo's archive. CI counts a squash- or rebase-merged branch as merged when its last commit on the folder is in `main`'s history or `main` has held exactly the branch's version of the folder, never by commit times.
- **The repo's dates and agentic first (094):** a synced proposal is created when the repo says (the header's `**Created:**` day, timed by `state.json`'s proposal time when that's the same day; else that time; else the commit that added `change.md`), and each task the sync closes is dated by the commit that ticked its box (`sync/authors.ts`, read by the plugin, CI and the self-sync with the author). A task a commit message or a person closed keeps its date and `done_by`; dates git can't tell (a shallow clone) leave the stored ones. Proposals and tasks a sync dated earlier are corrected on the next sync (`repoDatesStale`). The proposal page's history shows the phases `state.json` records as "Approved / Tasks planned / Verified / PR raised / Archived in the repo" (`meta.repoPhases`, pinned as `repo:<phase>`). "Shipped to Prod per week" and "Released this month" count only proposals a Prod deployment released (`deployment.released`, not voided), not the repo's archive. A task counts as ticked only in a commit that turns its `[ ]` into `[x]`, so rewording, reordering or reformatting a ticked task doesn't re-date it. Repo dates in the future (a skewed clock) read as unknown (`server/repo-time.ts`, with the push's skew rule), and phase times a sender didn't read (an older plugin) or dated in the future keep the stored ones; one rule (`resolveRepoPhases`) for the push, the self-sync and `sync_proposal`, applied on the locked row. Each stored phase keeps the read that first recorded its time (`meta.repoPhases.<phase> = { at, source }`), and its history line names it. 096: a phase the repo reached stays recorded (a read that leaves it out keeps it) while its proposal is live, under any folder name, so a change renamed on the default branch keeps its phases; once the proposal is withdrawn (its folder gone), a folder that comes back or takes its number starts from its own read (`storedPhasesFor`); stored entries are read one by one (a malformed one is skipped), a read is recorded only from `<ref>@<sha>`, and every writer refuses a `committedAt` in the future (`commitTime`) and treats a future `releasedAt` as unknown. In Prod is one rule (`server/in-prod.ts`) for the card, the CSV, the chart, the month count, the pin offers and voids. The Owner line is read by tokens (`sync/owner-line.ts`). On the all-projects Proposals page, once some project is agent-first, the repo line leads and manual creation is a plain "Add by hand" (`ui/proposals-action.ts`); an agent-first project's Proposals tab shows its repo line.
- **Duplicate change numbers (089):** the reader keeps every folder; two folders sharing a number are both marked `duplicate`. Every sync (push and self-sync) skips them with "two changes numbered <NNN>: <dir>, <dir>", leaves that key's proposal untouched, and sets `needsReview` (`delivery.sync_push.needs_review`, shown as Needs you). `scripts/check-change-numbers.mjs` fails a PR that adds a folder reusing a number, judged on what the merge produces (merge base, head and main's tip); the pairs already on `main` (062, 074, 075) are reported, not failed.
- **Self-sync (039, reduced by 008):** `sync/` imports a repo's `.specclaw/changes` into a project through `sync_proposal`'s service, tasks included (`pnpm --filter @amax/delivery sync:specclaw`). CI no longer runs it (089); it stays for a self-hosted amax that prefers the direct path, and skips duplicate numbers the same way
- **Who owns a phase (044):** a synced proposal's phase up to Verified belongs to the repo, so `move_proposal` refuses a specclaw row. Released belongs to Prod deployments, so a sync never moves a Released proposal back (an archived change may still sync as Released). A Prod deployment records each proposal's phase before release (`deployment.prior_phases`). Voiding it puts exactly that phase back, and Verified is the fallback for records from before 044. From then on the sync follows the repo again.
