- [minor module-standard] `modules/time/db/migrations/0009_entry_proposal.sql:3` Time's migration adds a foreign key into another module's schema (`references delivery.proposal(id)`). The module standard says migrations touch only the module's own schema and that a module can be switched off. This hard database link ties Time to Delivery's table. Fix: keep `proposal_id` as a plain uuid that is validated through `getProposalRef`, which the code already does. (round 1) <!-- fp:4cda07f766f6 -->
- [minor module-standard] `modules/delivery/server/pin-offers.ts:86` A proposal's pin offers 'Log time on <key>' (the `log_time` tool) after checking only Time's permission. It never checks `hasModule('time')`. With Time disabled, the chip fills a prompt for a tool that does not exist. Fix: guard this optional integration with `hasModule('time')`. (round 1) <!-- fp:3a8b7d0299d3 -->
- [minor B6] `modules/delivery/chat-suggestions.ts:35` `decodeURIComponent` runs on the raw route segment in `pageLabel`, `proposal()` and `ProposalsPage`. A malformed escape throws `URIError` instead of reaching the 'Proposal not found' path. Fix: wrap the decode, or rely on the router's own decoding. (round 1) <!-- fp:6f1a49fee59f -->
- [minor B6] `modules/time/server/proposal-hours.ts:31` `setProposalHours` is a `defineService`, so it opens its own transaction on a second pool connection while the handler's transaction still holds the advisory locks and its `onceForEvent` claim. Sorted locks keep the ordering safe. But each refresh holds two connections, and if the handler's transaction fails after the service commits, the retry writes a second audit row for the same event. Consider passing the totals back so the write happens after the handler's transaction, or document the two-connection need for small pools (such as Hyperdrive). (round 3) <!-- fp:7eb9b43148c8 -->
- [minor R3] `modules/delivery/pins.ts:59` `pinOf.event` sets the resolved id to the proposal's id, not the line's id. The registry's pin check therefore treats every line of a proposal as the same record: a pin with a wrong `line` but the right `proposalId` still passes. Key the pin on proposalId plus line, for example `id: "line"` or a composite, so the check proves it reached that exact line. (round 3) <!-- fp:0c65a17e4532 -->
- [minor B3] `packages/core/src/installed.ts:21` `provided()` returns an empty slot both when no installed module fills it and when `setProvided` was never called in this process. Only `apps/web/lib/registry.ts` sets it. Any entry point that renders or serves proposal detail without loading the registry would silently show 'no time logged' instead of 'unknown'. `hasModule` already tells these apart with null. Do the same here: start with null and fail or flag when a slot is read before it is set. (round 3) <!-- fp:9c69c4b8caf0 -->
- [minor B3] `modules/time/server/proposal-lines.ts:52` Applying the visibility rule before the cap made the page read unbounded: for a viewer who may see few or none of a proposal's time lines, every page load reads all of the proposal's time audit rows, 200 at a time, inside the request transaction. Bound it, for example with a maximum number of batches that reports the history as partial, or by pushing the owner/approver condition into SQL. (round 4) <!-- fp:6d2788e523a7 -->
- [minor B3] `modules/delivery/server/proposal-detail.ts:58` When Time is switched off, the refusal reuses `invalid(...)`, which carries `code: "invalid_input"` and `retryable: false`. Both signals say the caller's input is wrong and that retrying won't help. Neither is true here: the line id is valid, and the same read works again once Time is back. Chat's pin path only shows the message, so it isn't hurt. An MCP client, though, sees an input error for what is really 'unavailable'. Fix: add a distinct refusal in `refusal.ts`, for example code `unavailable` with retryable true, and match on that code in the review-2 table. (round 5) <!-- fp:8bdeff9e1a28 -->
